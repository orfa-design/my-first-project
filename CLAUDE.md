# Study Hub

Особистий вебзастосунок однієї студентки-заочниці для організації навчання.
Повна специфікація та прийняті рішення: `docs/SPEC.md`.

Стек: Next.js 16 (App Router, Cache Components) + TypeScript + Tailwind 4, PostgreSQL
(Supabase) через драйвер `postgres`, без ORM. Вхід — один пароль (`APP_PASSWORD`).

## Структура

- `db/migrations/*.sql` — схема бази; `npm run db:migrate` застосовує нові файли.
- `src/lib/schemas.ts` — zod-схеми, спільні для форм і CLI.
- `src/lib/data/*` — усі запити до бази. Сторінки й дії ходять у базу лише через них.
- `src/lib/hub.ts` — команди для AI; `scripts/hub.ts` — CLI над ними; `src/app/api/hub` — той самий вхід по HTTPS.
- `src/app/*` — сторінки. Дані читаються в async-компонентах усередині `<Suspense>` після `await connection()`.

Перевірки перед комітом: `npm run typecheck && npm run lint && npm run build`.

## Робота з навчальними даними

Основний спосіб наповнення — чат: користувачка надсилає повідомлення викладача, оголошення,
розклад тощо, а ти записуєш це в Study Hub командами CLI:

```bash
npm run hub -- help              # усі команди та поля
npm run hub -- summary           # поточний стан (як на головній)
npm run hub -- subject find "економіка"
npm run hub -- task create '{"title": "...", "subject_id": "...", "due_date": "2026-11-20"}'
npm run hub -- class import - < classes.json   # розклад: масив занять на конкретні дати
npm run hub -- grade create '{"title": "Модульна", "subject_id": "...", "score": 18, "max_score": 20}'
```

Якщо `node_modules` немає (нова хмарна сесія), спершу виконай `npm install`.
У хмарних сесіях CLI працює через сайт: потрібні змінні середовища `HUB_URL` і `APP_PASSWORD`.
Якщо їх немає — скажи користувачці додати їх у налаштуваннях середовища (не проси пароль у чаті).

Довгий JSON (з текстом повідомлення) передавай через stdin: `... task create - <<'JSON' ... JSON`.

### Правила

1. **Спершу визнач, що це.** Завдання / дедлайн, вимога до оцінювання чи допуску, результат
   оцінювання, інформація про предмет або викладача, зміна дати — чи просто інформаційне
   повідомлення, яке нікуди записувати не треба. Одне повідомлення може містити кілька речей.
2. **Шукай перед створенням.** `subject find` / `task find`. Якщо запис уже є — `update`, а не новий.
   `create` сам відмовить (код 2) на схожий запис; `--force` — лише коли ти впевнений, що це інше.
3. **Нічого не вигадуй.** Невідоме поле не заповнюй. Не підставляй дату, час, предмет чи бал «на око».
4. **Неоднозначне — уточни.** Якщо не зрозуміло, до якого предмета це, або дата суперечить наявній —
   запитай. Якщо дані записати варто, але частина під сумнівом — збережи з `"needs_review": true`
   і скажи, що саме перевірити.
5. **Зберігай джерело.** Текст оригінального повідомлення — у `source_text`, посилання — у `source_url`.
6. **Не перезаписуй без підстав.** `update` змінює лише передані поля. Не очищай і не замінюй
   наявний опис, вимоги чи результат, якщо нове повідомлення цього прямо не стосується —
   доповнюй.
7. **Відносні дати** («до наступної п'ятниці») рахуй від сьогоднішньої дати за київським часом
   і назви в відповіді конкретну дату, яку записав.
8. **Статуси.** `submitted` — здано, оцінки ще немає; `completed` — зараховано / оцінено;
   `needs_revision` — повернули на доопрацювання. Результат («18/20», «зараховано») — у `result`.
   Відсутня оцінка ≠ нуль.
9. **Звітуй коротко:** що створено чи змінено (назва, предмет, дедлайн) і що лишилося неясним.
10. **Розклад — це заняття, а не завдання.** Пари, екзамени й заліки записуй через `class`
    (`kind`: lecture, practice, lab, consultation, exam, credit, diff_credit, other) з конкретною
    датою. Завдання — лише те, що треба зробити чи здати. Пару без відомої дати не записуй —
    скажи, що треба уточнити. Перенесення — `class update` з новою датою/часом; скасування —
    `"status": "cancelled"` (не видаляй).
11. **Оцінки — у журнал** (`grade`): бал і максимум числами, лише якщо їх названо;
    «зараховано» — у `result_text`. Середній бал не рахуй.

Етап 3 (матеріали, база знань, пошук) і регулярний щотижневий розклад ще не реалізовані —
не намагайся записати такі дані в інші поля; скажи, що відповідний розділ з'явиться пізніше,
а важливе можна поки зберегти в `notes` предмета.
